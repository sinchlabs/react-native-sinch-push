# Example apps for `react-native-sinch-push`

Four example apps that exercise the SDK across every combination of React Native
runtime and architecture we support:

| App                          | React Native | Expo SDK | Architecture | Codegen |
| ---------------------------- | ------------ | -------- | ------------ | ------- |
| `examples/bare-0.74-old/`    | 0.74.7       | —        | **old** (bridge)      | bridge module   |
| `examples/bare-0.76-new/`    | 0.76.9       | —        | **new** (TurboModule) | codegen spec    |
| `examples/Expo52Old/`        | 0.76.9       | 52.0.49  | **old** (`newArchEnabled: false` in `app.json`) | bridge module |
| `examples/Expo52New/`        | 0.76.9       | 52.0.49  | **new** (default)     | codegen spec    |

Each app installs the SDK via `file:../react-native-sinch-push` (a path
relative to the app's `package.json`). The SDK itself is consumed in dev mode,
so changes to the SDK source are picked up on the next Metro / native rebuild.

All eight targets build cleanly on macOS with:

- Xcode 26.6 (iOS SDK 26.5)
- Node 25.9
- JDK 17 (Zulu) — RN 0.74 / 0.76 Gradle requires 17, not the system 23
- CocoaPods 1.16.2

> **Manual testing only.** Builds are verified; you run the apps and validate
> the runtime behaviour.

## What each demo screen does

All four apps render the same screen (`examples/_shared/DemoScreen.{ts,js}`):

- A **status panel** showing the SDK's `initialized` flag, the latest captured
  device token, and the current identity.
- A **Configuration** section where you enter your `projectID`, `clientID`,
  `configID`, and choose the env (`eu1` / `us1` / `custom`).
- An **Identity** field whose value is the `userID` we'll sign for `setIdentity`.
- Four buttons:
  - **Initialize** → calls `SinchPush.initialize(config)`.
  - **Set Device Token (random)** → generates a synthetic token and calls
    `SinchPush.setDeviceToken(...)`.
  - **Set Identity** → derives `HMAC-SHA-512(userID, devSecret)` in JS and
    calls `SinchPush.setIdentity(...)`. The dev secret is hard-coded in
    `DemoScreen` — see the warning below.
  - **Remove Identity** → calls `SinchPush.removeIdentity(...)`.
- A live **Event log** of every `onTokenReceiveHandler`,
  `onPushReceiveHandler`, and `onInAppMessageHandler` payload the SDK emits.

> ⚠️ The example signs the identity **in JS** using a literal hard-coded
> secret. Real apps must sign on the **backend** with the secret from the
> Sinch Build Dashboard.

## AppDelegate patching

The SDK exposes its public Objective-C surface in
`react-native-sinch-push/ios/SinchPush.h`. Each app's `AppDelegate.mm` (or
`AppDelegate.swift` for Expo) imports that header and forwards the three
APNs callbacks to `[SinchPush did...]` before delegating to `super`. Example:

```objc
#import <SinchPush.h>

- (void)application:(UIApplication *)application
    didRegisterForRemoteNotificationsWithDeviceToken:(NSData *)deviceToken
{
  [SinchPush didRegisterForRemoteNotificationsWithDeviceToken:deviceToken];
  return [super application:application didRegisterForRemoteNotificationsWithDeviceToken:deviceToken];
}
```

Push capability / background mode / Android `POST_NOTIFICATIONS` are already
configured in each app's `Info.plist` and `AndroidManifest.xml`.

## Build & run

### Prerequisites

- macOS with Xcode 26.6 (iOS Simulator 18.x runtime present).
- Node 18+ (the apps use `nvm`'s Node 25).
- JDK 17 (RN 0.74 / 0.76 Gradle). We used:
  `/Library/Java/JavaVirtualMachines/zulu-17.jdk/Contents/Home`.
- Android SDK at `$ANDROID_HOME` (we used `/Users/emems/Library/Android/sdk`).
- `LANG=en_US.UTF-8` exported (CocoaPods otherwise refuses to run on Ruby 4).

### One-time SDK prep

Each example links the SDK through a `file:` install, which means the SDK's
built artifacts (`lib/`) need to exist and be fresh. From the repo root:

```bash
npm run prepack
```

(If you've changed the SDK's TypeScript source, re-run this before
rebuilding any example. The SDK's `ios/generated/` folder is regenerated by
the host app's `pod install` / Gradle, so you can leave it alone.)

### Build all eight targets

```bash
# iOS — always export LANG for CocoaPods + UTF-8
export LANG=en_US.UTF-8

# Bare 0.74 + old arch
cd examples/bare-0.74-old/ios && pod install && cd ..
xcodebuild -workspace ios/Bare074Old.xcworkspace -scheme Bare074Old \
  -configuration Debug -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' build CODE_SIGNING_ALLOWED=NO

# Bare 0.76 + new arch
cd examples/bare-0.76-new/ios && pod install && cd ..
xcodebuild -workspace ios/Bare076New.xcworkspace -scheme Bare076New \
  -configuration Debug -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' build CODE_SIGNING_ALLOWED=NO

# Expo 52 + old arch
cd examples/Expo52Old/ios && pod install && cd ..
xcodebuild -workspace ios/Expo52Old.xcworkspace -scheme Expo52Old \
  -configuration Debug -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' build CODE_SIGNING_ALLOWED=NO

# Expo 52 + new arch
cd examples/Expo52New/ios && pod install && cd ..
xcodebuild -workspace ios/Expo52New.xcworkspace -scheme Expo52New \
  -configuration Debug -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' build CODE_SIGNING_ALLOWED=NO

# Android — every example needs JDK 17 on PATH
export JAVA_HOME=/Library/Java/JavaVirtualMachines/zulu-17.jdk/Contents/Home
export PATH=$JAVA_HOME/bin:$PATH
export ANDROID_HOME=/Users/emems/Library/Android/sdk

for app in bare-0.74-old bare-0.76-new Expo52Old Expo52New; do
  (cd examples/$app/android && ./gradlew assembleDebug --no-daemon)
done
```

### Run

```bash
# Bare 0.74 — old arch
cd examples/bare-0.74-old && npx react-native run-ios

# Bare 0.76 — new arch
cd examples/bare-0.76-new && npx react-native run-ios

# Expo 52 — old arch
cd examples/Expo52Old && npx expo run:ios

# Expo 52 — new arch
cd examples/Expo52New && npx expo run:ios
```

## Known build issues baked into the Podfile / examples

These are the workarounds applied to make the four apps build on Xcode 26 +
iOS SDK 26. They're all in `examples/<app>/ios/Podfile` so a fresh
`pod install` reapplies them.

1. **Codegen spec C++ headers leaked into the SDK modulemap.** RN 0.76's
   experimental codegen emits a TurboModule spec (`RNSinchPushSpec.h`)
   inside the SDK pod's umbrella header. When the Swift driver tries to
   scan the SDK's module, it picks up `<utility>` / `<optional>` /
   `<cassert>` from `RCTRequired.h` transitively. Fix: drop
   `module * { export * }` from the SDK's `.modulemap`.
2. **Duplicate codegen symbols across pods.** The experimental codegen
   also embeds `FBReactNativeSpec-generated.o` into *every* pod's static
   library. With new arch **off**, we strip those codegen source files
   from each pod's `source_build_phase` so the codegen lives only in
   the single `ReactCodegen` target.
3. **`fmt` consteval in RN 0.76's vendored copy is rejected by Xcode 26's
   clang.** Patch `Pods/fmt/include/fmt/base.h` to hard-disable
   `FMT_USE_CONSTEVAL` and gate the auto-detection block behind `#if 0`.
4. **Expo SDK 52's `EXNativeModulesProxy.mm` uses `#ifdef
   RCT_NEW_ARCH_ENABLED` around `ExpoFabricView`.** `#ifdef` is true when
   the macro is *defined* — even when set to `0`. Patched the source to
   `#if RCT_NEW_ARCH_ENABLED` so it correctly checks the value.
5. **Expo per-source `COMPILER_FLAGS` override `GCC_PREPROCESSOR_DEFINITIONS`.**
   When `newArchEnabled: false`, we post-process the `Pods.xcodeproj` to
   append `-DRCT_NEW_ARCH_ENABLED=0` to every source file's `COMPILER_FLAGS`.

> Why isn't any of this fixed in the SDK itself? Because the underlying
> problems are RN 0.76 / Expo SDK 52 / Xcode 26 compatibility issues, not
> bugs in `react-native-sinch-push`. Upgrading any of those three
> (RN 0.78+, Expo SDK 53+, or Xcode < 26) removes the need for most of
> the Podfile patches.

## Manual-test checklist

For each app, after pressing **Initialize**:

- [ ] Status panel flips to `initialized: yes`.
- [ ] On iOS Simulator the app will request push permission the first time;
      grant it. On Android the `POST_NOTIFICATIONS` permission prompt appears
      on Android 13+; grant it. The status panel then shows the device
      token.
- [ ] Press **Set Device Token (random)**. The log shows a new INFO row
      confirming the synthetic token; the status panel updates.
- [ ] Press **Set Identity**. With real `projectID` / `clientID` /
      `configID` values, the Connect-RPC call to
      `IssueTokenWithSignedUuid` + `Subscribe` should succeed. With the
      placeholder values from the demo, you'll see a network error logged
      in the INFO row — that's expected.
- [ ] Trigger a remote push (using a Sinch Dashboard campaign, or the
      simulator's `simctl push` / `adb shell cmd notification post`).
      The push should appear in the event log as a PUSH row, and if it
      carries a `protobufPayload` you also see an INAPP row.
- [ ] Press **Remove Identity**. The log shows `removeIdentity ok`.
